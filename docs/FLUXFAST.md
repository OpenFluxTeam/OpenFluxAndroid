# FluxFast — собственный скоростной протокол OpenFlux

Статус: **v1, экспериментальный транспорт ядра** (`fluxfast`). Реализация —
`OpenFlux/transport/fluxfast.go`, регистрация типа — `transport/registry`,
клиентская модель — `TransportType.FLUXFAST`. Замеры скорости ещё не
проводились (см. «Что дальше»): документ фиксирует дизайн и ожидаемые
свойства, а не измеренные цифры.

## Зачем свой протокол, если есть `direct`

Нынешний быстрый путь — `direct`: один TCP-поток между телефоном и нодой.
У TCP-носителя под туннелем есть два врождённых потолка:

1. **Head-of-line blocking.** Один потерянный сегмент останавливает все
   потоки туннеля, пока не придёт ретрансмит, — хотя потерянный пакет мог
   принадлежать одному соединению из пятидесяти.
2. **TCP поверх TCP.** Внутренний TCP (gVisor) и внешний TCP ядра оба
   ретранслируют и оба режут окно по потерям; таймеры складываются,
   скорость на потерейном канале падает сильнее, чем у одного стека.

FluxFast — носитель на **UDP-датаграммах** (принцип WireGuard, наш
wire-формат): потеря датаграммы — просто потеря IP-пакета для внутренних
стеков, они чинят её сами, каждый для своего соединения.

## Как устроен

FluxFast — «тупая труба», как `direct`: над ним без изменений едут слои
ядра — Session (переговоры, failover между носителями), Batched (коалесценция
пакетов, zstd-gate) и AES-256-GCM. Поэтому профиль может держать FluxFast
вместе с документными носителями в одной сессии, ссылки `openflux://`
носят его как dial-адрес, а нода слушает его на том же номере порта, что
и `direct` (TCP и UDP — разные пространства портов).

### Wire-формат v1 (заголовок 20 байт, big-endian)

| Смещение | Поле |
|---|---|
| 0..2 | magic `F1 FA` |
| 2 | версия (старший нибл, 1) \| тип (0 data, 1 ping, 2 pong) |
| 3 | флаги (бит 0: запись разрезана на фрагменты) |
| 4..12 | connection id отправителя (случайный на запуск транспорта) |
| 12..16 | sequence записи / nonce пинга |
| 16 | номер фрагмента |
| 17 | число фрагментов (1 = запись целиком) |
| 18..20 | длина payload |

### Ключевые решения

- **Фрагментация вместо IP-фрагментации.** Запись до 64 КБ режется на
  датаграммы с payload 1180 байт (датаграмма целиком < 1280-байтовой
  MTU-гарантии пути). Приёмник собирает по (sequence, номер), дубли и
  перестановки не страшны, несобравшееся за 3 с выбрасывается.
- **Надёжности на этом слое нет — намеренно.** Неполная запись не
  доставляется никогда; потерянное дочиняют внутренние TCP/QUIC.
- **Размер батча под датаграмму.** Носитель подсказывает батчеру
  `PreferredBatchBytes = 3 × chunk`: кадр из ~3 фрагментов переживает
  потерю 1 % с вероятностью 0,97, а кадр из 56 фрагментов — 0,57.
  Поэтому MTU туннеля объявлен 1280, а не 16000, как у TCP-потока.
- **Роуминг по connection id.** Нода принимает датаграммы знакомого id
  с нового адреса: переход Wi-Fi → LTE не рвёт туннель и не ждёт
  переподключения. Новый id занимает ноду только после 25 с тишины
  прежнего (как takeover у `direct`). Честное ограничение v1: id виден
  на проводе, on-path атакующий может его подделать и зачернить пира
  (шифртекст для него бесполезен, подделки режет AEAD replay window
  слоем выше). Path challenge — в планах v2.
- **0-RTT старт.** TCP-handshake нет: первая датаграмма сразу несёт
  hello сессии. Подключение клиента = первый ответ пира.
- **Живость.** Ping/pong носителя каждые 5 с тишины (держит NAT и адрес
  пира свежими), `IsConnected` гаснет после 30 с молчания, но сокет не
  пересоздаётся: следующая датаграмма оживляет носитель сама.
- **Приоритет.** Как `direct`, живой FluxFast предпочитается документным
  носителям (`OPENFLUX_FLUXFAST_FIRST=0` отключает), и помечен
  CheapBytes (zstd только при явной выгоде). `OnReliableStream` не
  объявлен: путь с потерями — внутренний стек остаётся на CUBIC, не Reno.

### Настройки

| Что | Как |
|---|---|
| Размер фрагмента | параметр носителя `chunk`, env `OPENFLUX_FLUXFAST_CHUNK` (по умолчанию 1180) |
| MTU туннеля | env `OPENFLUX_FLUXFAST_MTU` (по умолчанию 1280) |
| Очередь отправки | env `OPENFLUX_FLUXFAST_QUEUE_KB` (по умолчанию 512 КБ) |
| Предпочтение в сессии | env `OPENFLUX_FLUXFAST_FIRST=0` |

## Как включить

В профиле Session добавить транспорт **FluxFast** с адресом ноды
`host:port` (в приложении — рядом с Direct в списке транспортов).
Нода: тот же профиль на выходе слушает FluxFast на UDP-порту
`exitDirectPort`. CLI ядра: `--transports=fluxfast` с `--direct-dial` /
`--direct-listen` (адресные флаги у FluxFast и direct общие), либо
`Type = fluxfast` + `Dial = host:port` в `.conf`.

## Что дальше (v2 и замеры)

1. **Замеры по методике `TRANSPORT_PERFORMANCE.md`**: loopback/WAN,
   потери 0/1/5 %, сравнение `direct` vs `fluxfast` одним бинарём
   speedbench; без этого скорость — гипотеза, а не факт.
2. **FEC**: XOR-паритет 1 на N датаграмм — восстановление одной потери
   без RTT ожидания ретрансмита внутреннего стека.
3. **Path challenge** при роуминге (закрыть подделку conn id).
4. **`recvmmsg`/`sendmmsg` и GSO** на Linux/Android: меньше syscall
   на датаграмму на нагруженном выходе.
5. **Мастер ноды**: ставить FluxFast вместе с нодой из приложения
   (сейчас порт открывается профилем выхода вручную).
